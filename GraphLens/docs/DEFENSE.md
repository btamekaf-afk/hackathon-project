# Защита GraphLens

## Тема для заявки

Визуализация покрытия GraphQL API автотестами.

## Краткое описание

GraphLens — прокси-сервис, который анализирует GraphQL-запросы автотестов, сопоставляет их со схемой API и показывает покрытие типов и полей. QA-инженер видит непокрытые части схемы, переходит от поля к тестовым сценариям и сравнивает результаты прогонов. Проект реализован по кейсу Zunami «Сеть глазами Бога».

## Речь примерно на три минуты

В GraphQL один endpoint обслуживает множество типов и полей. Команда может регулярно запускать автотесты, но по успешному результату прогона трудно понять, какие части API они вообще запрашивают.

Мы сделали GraphLens. Сервис ставится между автотестами и GraphQL API. В настройках тестов меняется endpoint. GraphLens получает схему через introspection или SDL, разбирает входящий запрос и связывает выбранные поля с типами схемы. Запрос отправляется в API, а событие обращения сохраняется в базе.

Покажу это на учебном API магазина. У нас 30 доступных для учёта полей. Базовый набор состоит из трёх запросов. Он выбирает 14 полей, то есть примерно 47 процентов схемы. На графе видны типы с полным и частичным покрытием. Открываем User и видим, что email ещё не запрашивался.

Теперь запускаем расширенный набор. Добавились подробный профиль, карточка товара и корзина. Получаем 27 из 30 полей, или 90 процентов. В истории можно сравнить прогоны и увидеть конкретные 13 новых полей. Для каждого поля доступно название сценария, который к нему обращался.

Мы явно определили методику. Учитывается выбор поля в валидном запросе, включая алиасы, фрагменты, переменные и директивы. Повторное поле внутри одного запроса считается один раз. Ошибки ответа видны в журнале. Метрика позволяет оценить охват схемы запросами. Качество assertions требует дополнительной интеграции с тест-раннером.

В MVP работают прокси, загрузка схемы, граф, детализация, журнал, история, сравнение и экспорт. Данные локального запуска сохраняются в SQLite. В основе анализатора используется стандартная библиотека GraphQL.js. Следующим шагом мы добавили бы CI-порог покрытия, анализ изменения схемы и масштабирование отчётов для больших API.

## Демо по шагам

1. Запустите `npm ci`, затем `npm start`. Для начала репетиции используйте базовый прогон.
2. Покажите 47%, 14 из 30 полей и 3 запроса. Откройте User и поле email.
3. Переключитесь на «Все поля» и включите «Непокрытые».
4. Нажмите «Расширить демо». Покажите 90%, 27 из 30 полей и 6 запросов.
5. В истории отметьте оба прогона. Покажите новые поля и изменение процента.
6. В журнале откройте ProfileDetails. Покажите алиас, fragment и @include.
7. При запасе времени выполните FinishCoverage из README и доведите расширенный прогон до 100%.

Учебные числа воспроизводятся кодом. Время ответа зависит от среды. Для демонстрации без интернета установите зависимости заранее и используйте локальный сервер. Внешние веб-шрифты имеют системные fallback-шрифты.

## Ответы на вопросы жюри

**Что именно покрывается?**

Поля объектных и интерфейсных типов, достижимых из Query и Mutation. Единица учёта — Type.field. Процент показывает долю полей, выбранных хотя бы одним валидным запросом.

**Почему выбран анализ AST?**

AST позволяет учитывать структуру документа, выбранную операцию, алиасы, фрагменты и условия директив. Привязка к схеме позволяет различать одноимённые поля разных типов.

**Как связать запрос с тестом?**

Через заголовок X-Coverage-Test. Без него покрытие считается, но название сценария в отчёте отсутствует.

**Что происходит при ошибке сервера?**

Запрос остаётся свидетельством выбранных полей. HTTP-статус и число ошибок GraphQL фиксируются отдельно. Ошибка анализа даёт нулевой вклад в покрытие.

**Показываете ли реальные вызовы резолверов?**

Сейчас измеряется статический выбор полей. Для фактического исполнения нужна серверная трассировка, особенно для интерфейсов, union и частичных ошибок.

**Что если изменилась схема?**

У каждого прогона собственный снимок и хеш. Сравнение процентов доступно между одинаковыми снимками. Семантическое сравнение разных версий схемы входит в дальнейшее развитие.

**Сохраняются ли данные?**

Да, сохраняются прогоны, снимки схем и события запросов. Локально используется SQLite, в опубликованном варианте D1. Заголовки авторизации и значения variables в журнал не записываются.

**Что ограничивает масштабирование?**

В MVP отчёт агрегирует события прогона при чтении. Для крупных прогонов потребуется инкрементальная агрегация и пагинация. Схему большого API удобно отображать с группировкой и виртуализацией.

**Что уже проверено?**

Автоматизированные проверки анализатора и HTTP-обработчика, включая ошибочные и конкурентные запросы. Проверка на инфраструктуре заказчика потребует его endpoint, схемы и автотестов.
